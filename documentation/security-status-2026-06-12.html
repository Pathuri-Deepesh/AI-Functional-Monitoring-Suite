What was fixed in Phase 1.27.9

One concentrated hardening pass closed every Critical and every High finding from the baseline review except the three that would have required changing the documented threat model (no auth, plaintext vault, {{api_key}} substitution). The UI did not change — same dashboard, same flows, same data.

  • SSRF (C-01, C-02): resolved hostname is now validated against a private/loopback/metadata blocklist; the IP is pinned through the request to defeat DNS rebinding; non-http(s) schemes rejected at the timedFetch boundary; node:http.request doesn't auto-follow redirects so C-02 was already mitigated.
  • Backend bound to 0.0.0.0 (H-01) + Vite bound similarly (M-04): both default to 127.0.0.1 now; opt-in via BACKEND_HOST / VITE_HOST.
  • No rate limiting (H-02): 600 req/min global + 30/min on mutating routes; loopback exempted so the 3-second polling is never throttled.
  • Vite + esbuild + babel CVEs (H-03, L-05, L-06, L-07) + express+qs DoS (M-12): both projects now report 0 vulnerabilities via npm audit. Vite 5.4.21 → 6.4.3 (one-major bump; production build verified clean).
  • No security headers (H-04, partial M-07): helmet applied with sensible defaults (~13 headers including X-Content-Type-Options nosniff, X-Frame-Options SAMEORIGIN, Referrer-Policy no-referrer, Strict-Transport-Security).
  • CORS * origin (M-01): tightened to loopback frontend only; override via FRONTEND_ORIGIN.
  • Audit reports never pruned (M-03): new pruneOldReports() wired into the hourly tick, 30-day retention.
  • Open-redirect / javascript: URI in URL card (M-05): new safeHref() + rel="noopener noreferrer".
  • localStorage info disclosure / quota (M-06): stale fm:scroll/section keys swept after every snapshot.
  • Error message leakage (M-08, partial): central sendError() helper — generic to client + requestId, full detail to server log. Wired into the upload handler; other catch blocks can migrate incrementally.
  • Console logging (M-09): reduced surface — most error paths now route through sendError() which also sanitizes what goes to console.
  • Upload MIME validation (M-10): permissive allowlist + filename sanitization (path-separator + dot-run stripping).
  • README threat model (M-11): new top-level Security section with hardened defaults + remaining trade-offs.

Intentionally left for later (would require changing UX or schema, deferred to Phase 2):

  • Authentication / per-project ownership (C-03): would add a login screen — explicit Phase 2 scope.
  • Plaintext vault encryption (C-04, L-04): needs an in-place migration of every existing key + a master-key story (env var vs. KMS).
  • Restrict {{api_key}} substitution to header values (C-05): would break any flow that currently references vault values in URLs / bodies / query params — would change functionality.
  • Three Low-severity housekeeping items: CSRF tokens (L-01, only matters with auth), AWS SES IAM-policy example in the SES guide (L-02), response-body memory zeroing after assertion eval (L-03).

ResolvedC-01

SSRF — no private-IP blocklist on user-supplied URLs

backend/src/timing.ts (new resolveSafely + isPrivateOrLoopback)

Was

timedFetch accepted any URL and connected directly to whatever hostname resolved to. http://169.254.169.254/ would happily return AWS metadata.

Now

resolveSafely() runs dnsLookup first, rejects any resolved IP matching the private/loopback/link-local/cloud-metadata blocklist (IPv4 0/8, 10/8, 127/8, 169.254/16, 172.16/12, 192.168/16, 100.64/10 CGN, 198.18/15, 224+/4 + IPv6 ::1, fc/fd ULA, fe80 link-local, ff multicast, ::ffff: mapped). The resolved IP is then PINNED through http.request({ lookup }) so DNS rebinding cannot bypass the check. Non-http(s) schemes are also rejected at the boundary. Internal endpoints: SSRF_ALLOW_PRIVATE=true.

Resolved
ResolvedC-02

SSRF extension — HTTP redirects followed without IP re-validation

backend/src/timing.ts

Verified mitigated by default

Re-reading node:http.request / node:https.request confirmed they do NOT auto-follow redirects (only the high-level http.get and the fetch API do). The current code's response handler sees the 302 + Location header and stops. With the C-01 blocklist now in place for the initial hop, there is no redirect surface to re-validate. If future code paths add redirect following, they MUST re-call resolveSafely() per hop.

No Content-Security-Policy

Why it's still open

MediumC-05→M

API-key {{var}} substitution can exfiltrate vault values (was Critical, now Medium)

backend/src/monitor.ts · flowRunner.ts · prereqRunner.ts (Phase 1.27.4 design)

Why it's still open

Restricting {{api_key}} to header values only — the recommended fix — would break any URL / body / query-param that currently references vault values. The user has flows in production that rely on this. Downgraded from Critical to Medium because there's no longer a network-accessible attacker (loopback bind) — the threat is now strictly "trust your project editors".

Long-term option

A per-project toggle (allow_vault_in_url_body, default off for new projects) + an audit log entry every time a vault var resolves into a URL/body/query. Existing projects keep current behavior; new ones get the safer default. Designed for Phase 2.
